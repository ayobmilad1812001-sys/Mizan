1. Purpose and Document Authority

This document is the single authoritative specification for Mizan V1. Version 1.1 records the decisions taken while the database was implemented and verified against MySQL. Where it differs from V1.0 or any earlier paper, this document governs.

Schema accuracy. The schema reference in section 8.5 is generated from the running database (information_schema), not written by hand. Column types, keys and constraints in this document are therefore exactly what is deployed.

1.1 Design philosophy

PropertyWhat it demands of the implementation
Transactional integrityEvery business operation that touches more than one row succeeds completely or not at all.
Inventory traceabilityNo quantity ever changes without a stock movement recording the cause.
Concurrency safetyCorrectness is guaranteed by database locks and constraints, never by application checks alone.
AuditabilitySensitive actions answer: who, what, when, where, which record, what changed, why.
AccountabilityEvery operation carries the identity of the employee who performed it.
Historical integrityCompleted transactions are immutable. Corrections are new operations, never edits.
Defence in depth V1.1A business rule that the database can express is enforced there as well as in code, so a programming error cannot corrupt financial or inventory data.

2. System Overview and Scope

Mizan is an internal business management and inventory system for a retail business with warehouses in several cities. V1 serves one company and is not multi-tenant.

4. Global Business Rules

IDRule

BR-GLOBAL-02Every protected operation is authorised on the backend against the user's role permissions.

BR-GLOBAL-07Stock can never become negative by any operation, including adjustment. Enforced by CHECK and by application validation.
BR-GLOBAL-08Rows in a read-check-write sequence are locked with SELECT … FOR UPDATE until commit.

BR-GLOBAL-10 V1.1Completed documents (sales, sale lines, returns, return lines, refunds, receipts, adjustments, transfers, stock movements, audit entries) cannot be updated or deleted through the application. The only exception is the returned-quantity counter on a sale line.
BR-GLOBAL-11 V1.1Operations that a double click could duplicate carry an idempotency key under a unique constraint: sales, returns, stock adjustments and stock transfers. Purchase receipts are protected by one-receipt-per-order.

6. Supplementary Design Decisions

6.1 Multi-unit products

Goods are bought wholesale and sold retail. Each product has units (piece, dozen, carton) with a conversion factor and explicit per-unit prices; a carton is not priced by multiplying the piece price.

Governing rule. Stock and stock movements are always in the base unit. Every transaction line freezes unit_factor and stores base_quantity = TRUNCATE(quantity × unit_factor, 3).

  • Exactly one base unit per product, whose factor must be 1 (generated column + unique index + CHECK).
  • V1.1 A line's unit must belong to the line's product: composite foreign key (product_unit_id, product_id) → product_units(id, product_id) on purchase, transfer and sale lines.
  • V1.1 Adjustment lines hold balances only and are always in base units; the unit a clerk counted in is converted by the screen before saving.
  • V1.1 Returns are expressed in the unit that was sold.
2 cartons sold, factor 24     base_quantity = 48    stock decreases by 48 pieces
profit = line_total − (base_quantity × unit_cost per base unit)

6.2 Discounts, tax and line amounts

  • Discount is a percentage on the whole invoice, default 0. Percentage and amount are both stored.
  • V1.1 tax_rate is frozen on each sale, so later setting changes never alter the meaning of old invoices. Tax is applied after the discount.
  • The discount is distributed across lines. Each line stores its discount_share, its line_total and its net_unit_price.
  • Refunds use the net (post-discount) price: a piece sold at 1000 with a 20% invoice discount refunds 800.
discount_amount = ROUND(subtotal × discount_percent / 100, 3)
tax_amount      = ROUND((subtotal − discount_amount) × tax_rate / 100, 3)
total           = subtotal − discount_amount + tax_amount
line_total      = ROUND(quantity × unit_price, 3) − discount_share
net_unit_price  = ROUND(line_total / quantity, 3)

All five formulas are CHECK constraints in the database.

6.4 Warehouse access

No user-to-warehouse table. A sales employee sells from whichever warehouse holds stock. warehouses.supervisor_id is informational, not an access restriction. The warehouse list on the sales screen belongs to sales.create, not warehouses.view.

6.5 Document numbering UPDATED

References INV, PO, ADJ, TR, RET are issued per year from document_sequences. DocumentSequence::next() performs one atomic statement:

INSERT INTO document_sequences (document_type, year, last_number) VALUES (?, ?, LAST_INSERT_ID(1))
ON DUPLICATE KEY UPDATE last_number = LAST_INSERT_ID(last_number + 1)

Called inside the document's transaction, a rollback releases the number. Verified with two concurrent processes issuing 80 numbers: no duplicates, no gaps. Format PREFIX-YYYY-NNNNN; the invoice prefix comes from settings.

6.6 Categories, customers, deletion

  • Categories are flat.
  • sales.customer_id is nullable (walk-in sales). A customer's phone is unique when provided.
  • Deactivation uses status (active / inactive). SoftDeletes are rejected: they hide rows silently, and a hidden product may still have stock on a shelf.

6.7 Authentication and sessions V1.1

  • "Remember me" is removed. Terminals are shared; a remembered login would record one employee's sales under another's name. The remember_token column does not exist and the User model disables the feature.
  • The login session ends when the browser closes (SESSION_EXPIRE_ON_CLOSE=true), with 120 minutes idle lifetime.
  • Invitations are valid for 24 hours, single use, stored as a SHA-256 hash.
  • The first admin is created by an interactive seeder that asks for the password with hidden input (at least 12 characters, letters and numbers). The password is never written to a file.
  • Pending: force a password change on first login when the deploying developer set the admin password (Appendix E).

6.8 Time zone V1.1

Application time zone Africa/Tripoli; MySQL session time zone +02:00 (a numeric offset works without MySQL time-zone tables, and Libya has had no daylight saving since 2013). This keeps database defaults and application timestamps identical and prevents invoices near midnight on 31 December from taking the wrong year.

6.9 Language

Arabic, right-to-left interface with Arabic data entry. SKUs, document references and numerals stay Latin, rendered with directional isolation and tabular figures.

7. Functional Requirements

7.1 Employee onboarding

admin creates account (status pending, no password) → invitation issued (24 h, hashed token)
→ employee opens link → sets own password → status active

The admin never sets an employee's password. Employees are disabled, never deleted.

7.2 Roles and permissions

51 system permissions in 11 modules (Appendix A). Roles are configurable; a role in use or a system role cannot be deleted. Re-running the seeders never overwrites role permissions an admin has customised; only the admin role is re-synchronised to hold every permission.

7.3 Products and units

SKU required and unique. Creating a product never creates stock. Inactive products and inactive units cannot be sold. Price changes never alter historical lines. Stock level: out at 0 (red), low at or below reorder_level (yellow), otherwise available.

7.4 Create sale

authenticated employee + idempotency key from the form
 → resolve the employee's OPEN session (never trust a client session id)     [service]
 → validate warehouse, products and units active, quantities > 0             [service]
 → BEGIN
     lock warehouse_stocks rows in a consistent order                       [service]
     verify stock in base units                                              [service + CHECK]
     compute discount distribution, tax, totals, net prices                  [service + CHECKs]
     issue invoice number                                                    DocumentSequence::next
     insert sale and lines (session must belong to the employee)             [composite FK]
     decrement stock, insert SALE movements with negative quantity           [CHECKs]
   COMMIT
 → invoice

7.5 Sales session

At most one open session per employee (database). Every sale and return attaches to the employee's own open session. Closing records expected cash, actual cash, the difference and notes; a shortage never blocks closing; the difference must equal actual minus expected. Closed sessions are never reopened.

7.6 Purchasing

Statuses draft → confirmed → received or cancelled. V1.1 Confirmation and cancellation record who and when, and the database rejects any status without its matching who/when columns. Receiving selects the warehouse, increments stock with PURCHASE_RECEIPT movements and can happen once per order in V1.

7.7 Stock adjustment

Reason is mandatory and cannot be blank. Each line stores previous, new and difference in base units; the difference must be the exact subtraction and cannot be zero. The resulting stock cannot be negative.

7.8 Stock transfer

Source and destination must differ (CHECK). Each line produces TRANSFER_OUT (negative) and TRANSFER_IN (positive) movements in one transaction.

7.9 Returns and refunds

  • Only cash sales can be returned, enforced in the database.
  • A return line must belong to the invoice being returned (two composite foreign keys sharing sale_id).
  • returned_quantity on the sale line can never exceed the sold quantity (CHECK), even under concurrent returns.
  • Refund = one per return, cash, and its amount must equal the return total exactly.
  • The return total is computed from net prices. On the final return of a line, the refund uses the remaining line amount so rounding never leaves the customer short. SERVICE
  • Reason mandatory and non-blank. The original sale is never modified.

7.11 Reporting and settings

Reports are read-only, permission-filtered, and use sale_items.unit_cost captured at sale time for profit. Seeded settings: company_name, company_phone, company_address, company_logo, currency (LYD), tax_rate (0.00), invoice_prefix (INV). Critical settings (currency, tax rate, invoice prefix) are audited on change.

8.2 The composite-key pattern V1.1

A foreign key over two columns proves that a row belongs to the right parent, not merely that both ids exist. The parent carries a unique index on the pair.

GuaranteeMechanism
A unit belongs to the line's product(product_unit_id, product_id) → product_units(id, product_id)
A sale is in the seller's own sessionsales(sales_session_id, user_id) → sales_sessions(id, user_id)
A return is in the returner's own sessionreturns(sales_session_id, user_id) → sales_sessions(id, user_id)
Only cash sales are returnedreturns(sale_id, sale_payment_method) → sales(id, payment_method) plus CHECK (sale_payment_method = 'cash')
A return line belongs to the returned invoicereturn_items(return_id, sale_id) → returns(id, sale_id) and return_items(sale_item_id, sale_id) → sale_items(id, sale_id)
Refund equals return totalrefunds(return_id, amount) → returns(id, total_amount)

8.4 Rules that services must enforce SERVICE

These need other rows, sums or live state that a CHECK cannot read. They were identified explicitly, one of them by testing that the database accepts it.

#Rule
1Sales and returns only in an open session (verified: the database accepts a sale on a closed session).
2Invoice subtotal equals the sum of its lines; return total equals the sum of its lines.
3A return line's unit price equals the sale line's net unit price; its base quantity uses the sale line's factor.
4Sufficient stock checked under row lock before decrementing (the CHECK is the last line of defence).
5Products, units, warehouses, suppliers and customers are active when used.
6A line's frozen unit_factor equals the unit's factor at the time of the transaction.
7Stock movements are created only by the inventory service; the polymorphic reference cannot be a foreign key.
8Expected cash at closing = opening float + cash sales − cash refunds for that session.

9. Technical Architecture and Implementation Status

9.2 Model conventions V1.1

  • 30 models, 9 enums (UserStatus, SettingType, ActiveStatus, StockMovementType, StockLevel, PurchaseStatus, SessionStatus, PaymentMethod, DocumentType).
  • Mass assignment: sensitive columns (role, status, password, is_system, created_by, is_base) are never fillable. Transaction and inventory models are fully guarded and written only by services.
  • Immutability: an Immutable trait blocks update and delete on historical models; SaleItem allows only returned_quantity.
  • Morph map (enforced): polymorphic columns store short stable aliases (user, role, setting, category, brand, warehouse, customer, supplier, product, product_unit, purchase, purchase_receipt, stock_adjustment, stock_transfer, sales_session, sale, return, refund), never class names, so renaming a class cannot break history.
  • Strict mode outside production: silently discarded attributes, lazy loading and missing attributes raise errors.
  • The return model is SaleReturn (table returns) because return is reserved in PHP. Reserved SQL words were avoided as column names.
  • Index names are kept within MySQL's 64-character identifier limit.

9.3 Deployment and environments

Warehouses are in different cities, so V1 is one internet-hosted web application with a single shared database. Per-terminal installations and branch-local servers with synchronisation are rejected. Development uses Laragon's MySQL 8.4.3 and Herd's PHP 8.4 from PowerShell; Laragon's own terminal ships PHP 8.3 and cannot run the project.

Schema changes on a database that holds data use php artisan migrate, never migrate:fresh. Migrations are grouped in batches so migrate:rollback undoes only the last one.
